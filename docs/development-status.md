# 개발 상태 — 2026-11-14

## 현재 단계

사용자는 현재 iPad만 사용하며 약 한 달 뒤까지 데스크톱 시험이 어렵다.
YouTube 음원 확보·Render 실험을 보류하고 박자 및 코드 인식 평가·개선으로 전환했다.
기존 음원 공급 코드는 보존하며 앱 설치·서버 구매·새 클라우드 계정 연결을 요구하지 않는다.
이전 사이트는 집 노트북에서 실행했다는 추가 설명이 있지만 같은 버전·같은 영상의 현재 비교는 없다.
Codespaces의 자동화 확인 오류는 서버 접속 제한의 유력한 증거이며 코드 회귀 배제나 원인 확정과 구분한다.

## 이번 작업의 완료 조건과 변경

엔진을 조정하기 전에 정답 박자 미입력 조건의 기준선을 확보한다.
인식 알고리즘·합성기·캐시 버전·사용자 교정은 변경하지 않았다.

- `beateval` 기본값을 자동 평가로 변경했다. `--meter-mode reference`는 정답 박자 지정 보조 평가다.
- `--tracker librosa`로 현재 CPU 기준선을 고정하고 `--json-out`으로 비교 가능한 기록을 남긴다.
- 비트 위치, 다운비트 위치, 완전한 마디 구간, 템포 오차, 마디당 펄스 수 일치를 구분한다.
- 음원·생성 조건 해시로 같은 입력인지 확인하고, 기록이 없거나 내용이 달라진 음원을 무조건 정답과 연결하지 않는다.
- 현재 코드를 그대로 보존해 이후 후보 엔진을 동일 평가 조건에서 비교할 수 있다.

## 실행과 결과

CPU 기준선 환경: Python 3.12.14, numpy 1.26.4, librosa 0.10.2.post1, scipy 1.13.1.
beat_this·torch는 설치되지 않았다. 현재 실제 추적 경로는 librosa다.
정답 박자 입력 조건과 자동 조건은 같은 합성 음원 16개의 SHA-256을 비교한다.

| 합성 평가 조건 | 비트 F | 다운비트 F | 마디 구간 F | 마디당 펄스 수 일치 |
|---|---:|---:|---:|---:|
| 자동: 정답 박자 미입력 | 98.2% | 72.9% | 68.8% | 13/16, 81.25% |
| 정답 박자 입력 | 98.2% | 85.1% | 87.5% | 입력값이므로 자동 인식 성능을 계산하지 않음 |

각 F는 곡별 평균이고 허용 오차는 ±70ms다. 마디 구간은 양 끝 경계가 모두 맞아야 한다.
비트·다운비트 F는 이전 정의대로 전체 추정 이벤트를 사용한다. 합성 음원 끝의 1초 여운에는
정답 비트가 없으므로 끝의 추가 검출도 오탐으로 센다. 마디 구간 지표는 음악 끝 경계를 포함하고,
그 뒤 여운 구간을 제외하므로 이벤트 F와 수치를 직접 비교하지 않는다.
두 조건 모두 템포 배수 오류는 0/16이었다. 합성 5곡 코드 평가는 변경 전후 모두 길이 가중 98.8%였다.

평가 명령:

```bash
python -m pytest tests -q
python -m chordapp eval --dir work/nov14-baseline/chords
python -m chordapp beateval --dir work/nov14-baseline/beats --regenerate --meter-mode auto --tracker librosa --json-out work/nov14-baseline/auto.json
python -m chordapp beateval --dir work/nov14-baseline/beats --meter-mode reference --tracker librosa --json-out work/nov14-baseline/reference.json
```

변경 전 pytest: 320 passed, 4 warnings. 변경 후: 333 passed, 4 warnings.
음원·JSON 상세 기록은 저장소에서 제외한 `work/nov14-baseline/`에 있으며 원본·교정 DB에 쓰지 않는다.
원래 명령의 다운비트 약 85%·박자 오인 0/16은 정답 박자를 입력한 결과였다.
오늘 자동 조건에서 수치가 낮아진 것은 평가 조건이 달라졌기 때문이며 엔진 회귀나 개선으로 해석하지 않는다.

## 발견한 구조적 한계와 다음 작업

1. 현재 librosa 경로는 박자표를 추정하지 않고 기본 4박을 쓴다. 3박 2곡·6펄스 1곡에서 모두 4박을 출력했다.
   임계값 보정으로 박자표 추정 기능이 생기지는 않는다. 후속 작업에서는 박자 추적기 후보를 CPU에서 비교한다.
2. `bpm078_4_4`와 `fast_harmony_124`는 비트 F가 약 97~98%인데 다운비트·마디 구간 F가 0%다.
   추정 다운비트가 정답 1박 대신 반복해서 3박에 놓였다. 저역 온셋과 백비트 감점으로 위상을 고르는
   `estimate_downbeats`의 가정과 특징을 먼저 검토하고 한 곡에 맞춘 가중치 조정은 하지 않는다.
3. 코드 평가 98.8%는 쉬운 합성 5곡에서 포화된 수치다. 실제 녹음이나 더 다양한 독립 표본 없이는
   일반적인 코드 인식 성능을 판단하지 않는다. 코드 경계 시점·화음 종류별 평가를 후속으로 보강한다.
4. 기존 `benchmark`는 새 예측에 교정을 얹어 정답을 만드는 한계가 있어 공식 평가로 사용하지 않는다.
   실제 음원을 사용자가 전체 검수한 뒤 고정된 정답 스냅샷을 저장하는 구조가 먼저 필요하다.

합성 6펄스 표본은 실제 6/8의 박 단위 해석과 구분한다. 템포 변화·변박·못갖춘마디·다양한 악기는
현재 세트에 충분히 포함되지 않았다. 이번 작업에서 인식 성능이 향상됐다고 주장하지 않는다.
