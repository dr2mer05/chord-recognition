# 코드 인식 & 화성학 대체 코드 추천 — M1 (MVP)

`chord-app-pipeline.md`의 1단계를 돌아가는 코드로 구현한 초기 버전.

**핵심 원칙 그대로**: 자체 모델 학습 없음, GPU 없음, 사전학습/DSP 조합 + 캐싱으로 비용을 억제하고
화성학 엔진에 개발력을 집중한다.

---

## 빠른 시작

```bash
pip install -r requirements.txt
```

```bash
python -m chordapp serve
```

`http://127.0.0.1:8000` 접속.

처음 켰을 때는 **유튜브 탭 아래의 "바로 보기 — 데모 음원"** 버튼을 누르면 된다.
유튜브 키도 yt-dlp도 없이 파이프라인 전체(비트·조성·코드 인식 → 대체 코드 → 재생 동기화)가
돌아가고, 정답 라벨이 있어서 인식 정확도까지 같이 나온다.

입력 경로는 네 가지다.

| 탭 | 필요한 것 | 상태 |
|---|---|---|
| **데모 음원** | 없음 | 항상 동작, 정확도까지 표시 |
| **유튜브** — 검색 | `YOUTUBE_API_KEY` | 키 없으면 비활성 |
| **유튜브** — 링크 입력 | 없음 (제목 조회는 공식 oEmbed) | 코드 DB HIT까지 항상 동작 / 오디오 분석은 아래 참고 |
| **코드 직접 입력** | 없음 | 항상 동작 (서버 연산 거의 0) |
| **로컬 파일** | 없음 | 항상 동작 |

오디오 없이 화성학 엔진만 써 보려면:

```bash
python -m chordapp subs Am --key C --prev F --next F
```

정답 라벨이 붙은 데모 음원을 만들어 파이프라인 전체를 돌려보려면:

```bash
python -m chordapp demo
```

```bash
python -m chordapp eval
```

## 설정

현재 상태 확인:

```bash
python -m chordapp config
```

키가 필요한 기능을 켜려면 `.env.example`을 `.env`로 복사하고 값을 채운다.
`.env`는 `.gitignore`에 들어 있고, 진짜 환경변수가 있으면 그쪽이 항상 이긴다.

**유튜브 검색 켜기** — Google Cloud Console에서:

1. 프로젝트 생성 (또는 기존 프로젝트 선택)
2. **API 및 서비스 → 라이브러리** → "YouTube Data API v3" → **사용 설정**
3. **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → API 키**
4. `.env`에 `YOUTUBE_API_KEY=발급받은키` 한 줄 추가 후 서버 재시작

무료 할당량은 하루 10,000 유닛이고 검색 1회가 100 유닛이라 하루 100회쯤 된다.
키는 만든 직후 "애플리케이션 제한 없음" 상태이므로, 노출되면 남이 쓸 수 있다.
Cloud Console에서 **API 제한을 YouTube Data API v3로 한정**해 두는 걸 권한다.

## 유튜브 연동과 약관 문제

파이프라인 1-8 체크리스트의 **"유튜브 오디오 추출 방식의 이용약관 적합성 검토"가 아직 미해결**이다.
그래서 법적 판단이 필요한 부분과 아닌 부분을 코드에서 분리했다.

| 기능 | 리스크 | 상태 |
|---|---|---|
| 링크 파싱 · 영상 ID 캐시 키 | 없음 (순수 로직) | 항상 켜짐 |
| 제목/채널 조회 (공식 oEmbed) | 없음 | 항상 켜짐, 키 불필요 |
| 검색 (YouTube Data API v3) | 없음 (공식 API) | `YOUTUBE_API_KEY` 설정 시 |
| **오디오 추출 (yt-dlp)** | **검토 대상** | **기본 꺼짐** |

오디오 추출은 기본이 꺼짐이고, 명시적으로만 켜진다:

```bash
pip install yt-dlp imageio-ffmpeg
```

`.env`에 `CHORDAPP_ENABLE_YTDLP=1` 추가 후 서버 재시작.

**현재 이 저장소는 개인·비상업 용도로 켜져 있다.** 상업 서비스로 전환한다면
위 검토 항목이 다시 살아난다.

끄더라도 **링크 입력 → 제목 조회 → 공개 코드 DB 조회(HIT)** 경로는 그대로 동작한다.

### 추출 관련 실무 메모

- **ffmpeg 필요.** 시스템에 없으면 `pip install imageio-ffmpeg`로 번들을 쓴다
  (`find_ffmpeg()`가 시스템 → 번들 순으로 찾는다). 전역 설치 강요를 피하려는 것.
- **player client를 여러 개 넘긴다** (`android,ios,tv,web`). 기본 web 클라이언트는
  `The page needs to be reloaded`로 실패했다. 유튜브가 추출 경로를 계속 바꾸므로
  추출이 깨지면 `PLAYER_CLIENTS`부터 손보면 된다.
- **audio-only DASH 포맷은 PO 토큰으로 막혀 있는 경우가 많다.** 그때는 오디오가 들어 있는
  통짜 mp4(포맷 18)로 폴백한다(`-f bestaudio/best`). 대역폭은 손해지만 확실히 된다.
- 받는 즉시 **22.05kHz 모노 wav**로 변환한다. 어차피 분석 전에 다운샘플되고,
  wav면 디코딩에 ffmpeg가 다시 필요 없다. 4분 곡이 약 5MB.

## 소스 분리 (Demucs)

```bash
pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu121
```

```bash
pip install demucs
```

`.env`에 `CHORDAPP_ENABLE_DEMUCS=1`. GPU가 없으면 CPU에서 몇 배로 느려지니
켤 가치가 없다. RTX 3060에서 4분 곡 분리가 약 35초, 결과는 `data/stems/`에 캐시된다.

파이프라인 문서의 설계를 그대로 따른다.

- 코드 인식 입력 = `other` + `bass` (믹스에서 보컬·드럼만 뺀 반주)
- 전위/슬래시 판별 = `bass` 스템 (저역 CQT 근사보다 정확)
- **비트 추적은 항상 원본 믹스** — 드럼을 빼면 온셋이 약해져 오히려 나빠진다

`--separate` / `--no-separate`로 곡별 강제 지정이 가능하고, 분리 여부는
캐시 키에 들어가므로 두 결과가 섞이지 않는다.

**분리된 스템은 원곡 마스터의 파생물이다.** 개인 이용 전용이고, 서비스에
다운로드·재배포 기능을 붙이면 안 된다(파이프라인 0장 경계선).

## 파이프라인

```
입력: 곡 제목 검색 / 유튜브 링크 / 로컬 파일
  │
  ├─ [A] 캐시 조회 (유튜브 영상 ID 또는 파일 내용 해시)  → HIT: 연산 0
  ├─ [B] 공개 코드 DB 조회 (제목 → 아티스트/곡명)        → HIT: 연산 0, 사람이 만든 정확도
  └─ [C] MISS일 때만 오디오 분석
         비트/조성 추정 → 코드 인식 앙상블 → 투표 + 조성 문맥 제약
         → 2패스 조성 재추정 → 저역 기반 전위 판정 → 비트/마디 스냅
  │
  └─ 화성학 엔진: 대체 코드 생성 + 랭킹 + "왜 되는지" 설명
  └─ 프론트엔드: 유튜브 플레이어 재생 동기화 + 대체안 토글
```

순서가 곧 비용 구조다. 오디오 분석은 마지막 수단이다.

## 구조

```
chordapp/
  theory/          화성학 엔진 — 의존성 0, 순수 파이썬

    chord.py         코드 파싱 · 구성음 · 표기

    substitution.py  대체 코드 규칙 13종 + 랭킹      ← 개발력을 가장 많이 넣은 곳
    stats.py         코드 전이 사전확률 (Hooktheory 자리)
  analysis/        오디오 → 코드 (librosa)
    audio.py         로딩 · HPSS · 비트/다운비트 · 크로마 · 조성
    templates.py     코드 템플릿 사전
    recognizers.py   크로마 템플릿(내장) + autochord/Chordino 어댑터
    hierarchical.py  단계별 인식: 근음 → 3화음 → 7화음 → 텐션
    ensemble.py      가중 투표 · 조성 제약 · 전위 판정 · 마디 스냅
    pipeline.py      오케스트레이션
  service/         캐시 · DB 조회 · 유튜브
    cache.py         SQLite 결과 캐시
    chord_db.py      공개 코드 DB 조회 레이어
    youtube.py       링크 파싱 · 검색 · 오디오 확보(기본 꺼짐)
    pipeline.py      [A]→[B]→[C] 오케스트레이션
  api/             FastAPI + 단일 파일 프론트엔드
  evaluation.py    MIREX 방식 WCSR (.lab 정답 파일)
  tools/synth.py   정답 있는 테스트 음원 생성기
```

`theory/`는 표준 라이브러리만 쓴다. 화성학 엔진만 떼어 쓰려면 나머지를 설치할 필요가 없다.

## 현재 정확도

합성 데모 5곡 기준 (`python -m chordapp eval`):

| 곡 | root | triad | seventh |
|---|---|---|---|
| pop_I_V_vi_IV | 99.2% | 99.2% | 99.2% |
| ballad_sevenths | 99.3% | 99.3% | 99.3% |
| minor_loop | 98.8% | 98.8% | 98.8% |
| eight_chord_loop | 98.5% | 98.5% | 98.5% |
| half_bar_changes (반 마디마다 전환) | 98.0% | 98.0% | 98.0% |
| **전체 (길이 가중)** | **98.8%** | **98.8%** | **98.8%** |

세션 시작 시점(96.4 / 96.4 / 93.9) 대비. 가장 크게 오른 건 화성 리듬이 빠른
`half_bar_changes`로 **86.0% → 98.0%**인데, 박자 기반 전이확률과 다운비트 수정 덕분이다.

> **주의**: 이 벤치마크는 소스 분리를 끄고 재야 한다. Demucs는 실제 녹음으로 학습돼서
> 합성음에 아티팩트를 만든다 (`half_bar_changes` 98.0% → 89.8%).
> `python -m chordapp eval`은 기본이 분리 없음이다.

속도: CPU에서 실시간의 **약 16~18배** (30초 음원 ≈ 2초). 첫 실행만 numba JIT 때문에 느리다.

**이 숫자를 그대로 믿으면 안 된다.** 합성 음원은 보컬도 드럼 배음도 리버브도 없어서
실제 녹음보다 훨씬 쉽다. 실측은 M2에서 McGill Billboard / Isophonics로 해야 하고,
`evaluation.py`는 이미 그 `.lab` 포맷을 읽도록 만들어 뒀다.

### 실제 상용 녹음에서의 확신도

정답이 없어 정확도는 못 재지만, 인식기의 확신도(1등·2등 템플릿 점수 차)는 잴 수 있다.
같은 파이프라인으로:

| | 구간당 평균 확신도 | 확신도 > 0.6 비율 |
|---|---|---|
| 합성 데모 | 0.83 | 92% |
| 실제 상용 녹음 (K-pop 발라드 1곡) | 0.43 | 9% |

**절반 이하로 떨어진다.** 보컬·리버브·더블링이 크로마를 오염시켜 1등과 2등 후보가
거의 붙어버리기 때문이다.

관측된 대표적 오류: 템포 옥타브 오류(74 BPM 곡을 161로), 나란한조 혼동.

### 소스 분리를 켰을 때 (같은 곡, 단일 사례)

| 구성 | 평균 확신도 | 확신도 > 0.6 | 앙상블 일치도 |
|---|---|---|---|
| 원본 믹스만 | 0.433 | 9% | 1.000 (의미 없음) |
| 분리 스템만 (`other`) | 0.418 | 12% | 1.000 |
| 분리 스템만 (`other`+`bass`) | 0.429 | **15%** | 1.000 |
| **스템 + 원본 앙상블** | 0.455 | 10% | **0.812** |

정직하게 말하면 **분리가 평균 확신도를 올려주지는 않았다.** 올라간 건 두 가지다.

1. **고확신 구간 비율 9% → 15%.** 확실한 곳은 더 확실해진다. 평균이 평평한 건
   원래 애매하던 구간이 분리 후에도 애매하기 때문.
2. **일치도가 처음으로 의미를 갖게 됐다 (1.000 → 0.812).** 인식기가 1개일 때는
   일치도가 항상 1.0이라 신뢰도 지표의 절반이 죽어 있었다. 이제 서로 다른 입력을
   보는 두 의견이 생겨서, 어느 구간이 실제로 애매한지 국소화된다.

중간에 얻은 교훈 하나: **`other` 스템만 쓰면 안 된다.** 베이스가 빠지면 근음 정보를
잃어서 원본 믹스보다도 나빴다(0.418 vs 0.433). 근음이 곧 코드 이름이다.

단일 곡·정답 없음이라 벤치마크가 아니다. 제대로 된 판단은 McGill Billboard가 필요하다.

알려진 약점은 **화성 리듬이 빠를 때**(반 마디마다 전환) 3도 관계 코드 혼동이다.
G를 Em7으로, Am을 Fmaj7으로 읽는 식 — 구성음 4개 중 3개가 겹치는데
크로마 창이 인접 코드까지 물어서 생긴다.

## 만드는 과정에서 실제로 잡은 버그

기록해 두는 게 나중에 도움이 될 것 같아 남긴다.

1. **비트 정렬이 한 박씩 밀림** — `librosa.util.sync(pad=True)`가 첫 비트 *이전* 구간을
   0번 열로 넣는다. 코드 진행은 다 맞는데 경계만 틀려서 정확도가 74%에 묶여 있었다.
   고치고 91%.
2. **7th 코드가 전혀 안 잡힘 (8%)** — 크로마를 C2부터 뜨니 베이스 기본음과 배음이
   스펙트럼을 지배해서 3화음만 남았다. C3~C7로 좁히니 **99%**.
3. **로마숫자 임시표** — Bb in C를 `#VI`로 표기했다. 장조는 트라이톤만 `#IV`,
   나머지는 내림이 관례다.
4. **세컨더리 도미넌트 누락** — 근음이 같으면 건너뛰게 짜서 `Am → A7`(V7/ii)이
   후보에서 빠졌다. 근음이 아니라 코드 전체로 비교해야 한다.
5. **조성 추정에 Krumhansl-Kessler를 잘못 씀** — KK는 선율 지속시간용이라 이끔음
   가중치가 평균보다 낮다. 코드 구성음에 적용하니 B가 있다는 사실이 오히려 C장조에
   불리하게 작용해서 `Dm7-G7-Cmaj7`을 G장조로 판정했다. 코드 전용 프로파일로 교체.
6. **2패스 조성 재추정이 나란한조를 뒤집음** — C장조 곡을 Am으로 "정정"했다.
   나란한조는 구성음도 다이어토닉 코드도 완전히 같아서 코드 내용만으론 구분이 안 된다.
   그 쌍에만 문턱을 크게 높였다.
7. **다운비트가 5곡 전부 틀렸는데 아무도 몰랐음** — 마디 첫 박 대신 4박을 짚고 있었다.
   원인이 세 겹이었다. (a) 격자 앞에 0.0을 끼워 넣어 위상이 밀림,
   (b) 온셋 곡선의 지연을 무시하고 비트 시각을 정확히 샘플링,
   (c) **전대역 온셋을 가산** — 스네어가 broadband 플럭스를 가장 크게 만드는데
   스네어는 여린박에 있다. 더할 게 아니라 뺄 항이었다.
   판정식을 `저역(킥) − 0.5 × 전대역(스네어)`으로 바꿔 5/5가 됐다.
8. **템포 옥타브 보정이 정확도를 98.8% → 31.3%로 파괴** — 짝수/홀수 박의 온셋 세기를
   비교해 "템포 2배"를 판별하려 했는데, 4/4 대중음악은 킥·스네어가 번갈아 나와서
   인접 박의 세기가 원래 다르다. 백비트를 템포 배수로 오인해 격자의 절반을 버렸다.
   되돌리고 미해결로 남겼다.

## 사용자 교정 루프 (`corrections.py`)

제품 기능이자 개발 도구다. 웹 UI에서 틀린 코드를 클릭해 고치면 저장되고,
다음에 같은 곡을 열 때 남아 있다.

```bash
python -m chordapp corrections     # 교정 현황
```

```bash
python -m chordapp benchmark       # 검수 완료한 실제 곡으로 정확도 측정
```

설계에서 중요한 두 가지.

**교정은 원본 인식 결과를 덮어쓰지 않는다.** 캐시에는 원본이 그대로 있고 교정은
별도 레이어로 얹힌다. 덮어쓰면 "교정된 결과 vs 교정"을 비교하게 되어
정확도 측정이 순환논법이 된다.

**곡 단위 '검수 완료' 표시가 따로 있다.** 틀린 코드만 골라 고친 표본은 편향돼 있어서
정확도를 계산할 수 없다("고친 것 중 몇 %가 틀렸나"는 항상 100%다).
곡 전체를 확인했다고 표시한 곡만 `benchmark`에 쓰인다.

교정 데이터는 MIREX `.lab`으로 내보낼 수 있어서, 나중에 공개 데이터셋 벤치마크와
같은 평가 코드로 돌아간다.

**왜 이게 우선순위 1번인가** — 이 프로젝트의 가장 큰 문제는 정확도가 아니라
**정확도를 측정할 수 없다는 것**이었다. 다운비트가 프로젝트 내내 5곡 전부 틀려 있었는데
어떤 테스트도 잡지 못했고, 템포 보정이 한 곡을 98.8% → 31.3%로 파괴한 것도
합성 벤치마크가 없었으면 그대로 나갔다. 그리고 그 합성 벤치마크마저 98.8%로 포화돼
이제 변별력이 없다. 실제 녹음 기준 숫자는 여기서만 나온다.

## 단계별 인식기 (`hierarchical.py`)

96개 템플릿을 한 번에 코사인 유사도로 비교하면 각 판단이 서로를 방해한다.
maj/min 판별은 사실 **3음 자리 두 칸만 보면 되는 문제**인데 템플릿 매칭에서는
나머지 음의 에너지에 묻힌다. 그래서 결정을 쪼갠다.

1. **근음** — 베이스 크로마(강한 사전확률) + 화성 크로마 + 조성, 비터비로 평활화
2. **3화음** — 근음 기준 3음·5음 자리만 비교
3. **7화음** — b7·M7·6 자리를 화음구성음 평균 대비 상대 세기로
4. **텐션** — 9음을, 더 엄격한 문턱 + 조성 안에 있을 때만

설계에서 중요한 판단 세 가지.

- **베이스로 근음을 확정하지 않는다.** 전위·슬래시 코드에서 베이스는 3음이나 5음을
  짚기 때문에, 확정하면 그 구간이 통째로 틀린다. 강한 가중치를 주되 화성 크로마가
  뒤집을 수 있게 둔다.
- **품질은 근음이 유지되는 구간마다 한 번씩** 정한다. 비트마다 정했더니 7음이 문턱
  근처에서 오르내려 `F / Fmaj7 / F / Fmaj7`로 깜빡였다.
- **3음이 애매하면 조성으로 푼다.** 실제 녹음은 보컬·리버브로 3음 자리가 자주 흐려지는데,
  억지로 고르면 `DbmMaj7` 같은 실존하지 않는 코드가 나온다(실제로 나왔다).
  그 근음이 조성 안에서 원래 무슨 3화음인지가 훨씬 믿을 만하다.

합성 데모에서는 템플릿 인식기와 동점(98.8%)이지만 **실패하는 지점이 다르므로**
둘 다 앙상블에 넣는다. 윈도우에서 autochord를 못 쓰는 상황에서 이게 실질적인 교차검증이다.
